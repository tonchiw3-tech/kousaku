**対象システム：香作（こうさく）／香作室** --- ## 1. システム概要 ### システムの目的【必須】 「香作（こうさく）／香作室」は、inimuの香水づくり体験を利用したいお客様が、体験内容の確認から予約登録まで行えるWebアプリケーションである。スタッフはログイン後、予約情報の一覧確認・ステータス変更・キャンセル管理ができる。予約情報をデータベースで一元管理し、予約業務の効率化を目指す。 ### システム構成図【必須】 ``` 【お客様・スタッフ】 PC・スマートフォン │ ▼ 【フロントエンド】 HTML / CSS / JavaScript Thymeleaf │ │ HTTP / JSON ▼ 【バックエンド】 Java / Spring Boot │ Controller │ Service │ Repository / MyBatis Mapper │ ▼ 【データベース】 MySQL │ 予約情報・スタッフ情報 ``` **各技術の役割** | 技術 | 役割 | | ----------------------- | -------------------- | | HTML / CSS / JavaScript | 画面表示・入力操作 | | Thymeleaf | Spring BootからHTMLを表示 | | Spring Boot | 予約登録・料金計算・予約管理 | | Controller | 画面・APIからの要求を受け付ける | | Service | 予約の業務処理を行う | | Repository / MyBatis | DBへの登録・取得・更新 | | MySQL | 予約情報・スタッフ情報を保存 | | Spring Security | スタッフのログイン認証 | | JUnit | プログラムのテスト | --- ## 2. 機能一覧 ### 機能一覧表【必須】 | No. | 機能名 | 概要 | 対応画面 | 優先度 | | ----- | -------------- | --------------- | ------ | ------ | | F-001 | トップ画面表示 | 香水づくり体験の紹介と予約入口 | トップ | Must | | F-002 | 体験内容表示 | 料金・所要時間・完成品の案内 | トップ・予約 | Must | | F-003 | 予約情報入力 | 日付・時間・人数・氏名等を入力 | 予約 | Must | | F-004 | 予約内容確認 | 入力内容・合計料金の確認 | 確認 | Must | | F-005 | 予約新規登録（Create） | 予約番号発行・DB保存 | 確認・完了 | Must | | F-006 | 予約一覧表示（Read） | 保存済み予約を取得・表示 | スタッフ管理 | Must | | F-007 | 予約詳細表示（Read） | 選択した予約の詳細を表示 | スタッフ管理 | Must | | F-008 | 予約更新（Update） | 予約ステータスを変更 | スタッフ管理 | Must | | F-009 | 予約削除（Delete） | 認証済みスタッフが確認操作後、予約情報をMySQLから物理削除する | スタッフ管理 | Must | | F-010 | スタッフログイン | ID・パスワードによる認証 | ログイン | Must | | F-011 | 入力チェック | 必須項目・形式・予約条件の確認 | 予約・確認 | Must | | F-012 | エラー表示 | 入力不備・通信エラー等を通知 | 各画面 | Must | | F-013 | レスポンシブ表示 | PC・スマートフォンへの対応 | 全画面 | Must | | F-014 | 予約件数表示 | 予約数を集計して表示 | スタッフ管理 | Should | | F-015 | 日付・状態での検索 | 条件に合う予約を抽出 | スタッフ管理 | Should | | F-016 | CSV出力 | 予約一覧をCSVで出力 | スタッフ管理 | Could | **優先度の定義** - Spring BootがHTMLを返す。 3. 体験内容と料金を表示する。 4. 予約ボタンから予約画面へ進む。 **正常時：** 体験内容・予約ボタンが表示される。 **エラー時：** 画面取得に失敗した場合、エラーページを表示する。 **遷移先：** 予約画面 ※体験内容はVer 1.0の演習用設定を維持する。実際の店舗情報として使用する場合は確認を要する。 ### F-003 予約情報入力 **機能名：予約情報入力** **機能ID：F-003** **画面レイアウト** 画面上部に体験内容・料金を表示し、中央に予約入力フォーム、下部に「予約内容を確認する」ボタンを配置する。 **入力項目一覧【必須】** | 項目名 | データ型 | 必須 | バリデーション | 備考 | | ------- | ------- | -- | -------------- | -------- | | 希望日 | Date | ○ | 土曜日・日曜日のみ（祝日判定は未実装） | 予約日 | | 希望時間 | String | ○ | 11:00 / 13:00 / 15:00のみ | 開催枠 | | 人数 | Integer | ○ | 1〜10の整数 | 予約人数 | | 氏名 | String | ○ | 空欄不可・100文字以内 | 予約者 | | メールアドレス | String | ○ | メール形式・254文字以内 | 連絡先 | | 年代 | String | ○ | 10代 / 20代 / 30代 / 40代 / 50代 / 60代以上 | 年齢区分 | | 利用区分 | String | ○ | FIRST / REPEAT | 初回・リピーター | サーバー側では希望時間を11:00・13:00・15:00、人数を1〜10名、年代を定義済みの6区分、利用区分をFIRST / REPEATに制限する。祝日データを用いる判定は未実装であり、現時点では土曜日・日曜日のみを予約可能日として検証する。 **処理フロー** 1. 利用者が予約情報を入力する。 2. 「予約内容を確認する」を押す。 3. 入力内容を検証する。 4. サーバーが合計料金を計算する。 5. 正常なら確認画面へ進む。 **正常時：** 入力内容を保持して確認画面へ遷移する。 **エラー時：** 該当項目にエラーを表示し、修正を求める。 **遷移先：** 確認画面 ### F-004 予約内容確認 **機能名：予約内容確認** **機能ID：F-004** **画面レイアウト** 入力された予約情報と料金を表示し、「修正する」「予約を確定する」ボタンを配置する。 **入力項目** 予約情報は入力画面から引き継ぐ。確認画面では原則として編集しない。 **料金計算** 合計料金 ＝ 5,500円 × 人数 例：2人の場合は11,000円。 **処理フロー** 1. 入力内容を表示する。 2. 合計料金を確認する。 3. 修正する場合は予約画面へ戻る。 4. 確定する場合は登録APIへ送信する。 **正常時：** 予約登録が成功した場合、完了画面へ遷移する。 **エラー時：** 入力不備や登録失敗時は完了画面に進まず、エラーを表示する。 **遷移先：** 予約画面・完了画面 ### F-005 予約新規登録（Create） **機能名：予約新規登録** **機能ID：F-005** **画面レイアウト** 確認画面の「予約を確定する」ボタンから処理を開始する。 **入力項目** 予約画面で入力した希望日・希望時間・人数・氏名・メールアドレス・年代・利用区分。 **処理フロー** 1. Spring Bootが予約情報を受信する。 2. サーバー側で入力チェックを行う。 3. 合計料金を再計算する。 4. `KS-`で始まる予約番号を発行する。 5. MyBatisを通じてMySQLに保存する。 6. 登録結果を返す。 **正常時：** HTTP 201を返し、予約番号を表示する。 **エラー時：** HTTP 400または500などを返し、登録失敗を通知する。 **遷移先：** 完了画面 ### F-006・F-007 予約一覧・詳細表示（Read） **機能名：予約一覧・詳細表示** **機能ID：F-006 / F-007** **画面レイアウト** スタッフ管理画面に予約一覧を表形式で表示する。詳細は行の選択などで表示し、画面を増やさずに確認できる構成とする。 **表示項目** 予約番号、希望日、希望時間、人数、氏名、メールアドレス、料金、ステータス。 **処理フロー** 1. スタッフがログインする。 2. Spring Bootが認証状態を確認する。 3. MyBatisがMySQLから予約を取得する。 4. 希望日・希望時間順に表示する。 **正常時：** 保存済み予約が表示される。 **エラー時：** 未認証の場合はログインへ誘導する。存在しない予約は404とする。 **遷移先：** スタッフ管理画面内 ### F-008 予約更新（Update） **機能名：予約ステータス変更** **機能ID：F-008** **画面レイアウト** 予約一覧から予約詳細を開き、予約対応の進捗をチェックリストで表示する。進捗は「予約内容を確認済み」「当日の受け入れ準備完了」「ワークショップ実施済み」の順に操作する。現在の予約ステータス、キャンセル操作、完了済み予約の訂正理由入力欄を表示する。 **予約ステータスの定義** | 値 | 表示名 | 説明 | | --- | --- | --- | | `RECEIVED` | 予約受付 | 予約登録直後の初期状態。 | | `CONFIRMED` | 予約確認 | スタッフが予約内容を確認済みの状態。 | | `READY` | 準備完了 | 当日の受け入れ準備が完了した状態。 | | `COMPLETED` | 体験完了 | 予約開始時刻を過ぎ、体験の実施完了を確認した状態。 | | `CANCELED` | キャンセル | スタッフがキャンセル処理を行った状態。予約データは保持する。 | **入力項目一覧** | 項目名 | データ型 | 必須 | バリデーション | 備考 | | ----- | ------ | -- | ------- | ------------------------------- | | 予約ID | Long | ○ | 存在確認 | 更新対象 | | ステータス | String | ○ | 定義済み値 | 5種類の定義値。`/status`では RECEIVED / CONFIRMED / READY / COMPLETED を使用し、CANCELED はキャンセルAPIで設定する。 | **処理フロー** 1. スタッフが予約詳細のチェックリストで進捗を操作する、またはキャンセル・訂正操作を行う。 2. 進捗更新はステータス更新API、キャンセルはキャンセルAPI、完了後の訂正は訂正APIへ送信する。 3. Serviceが現在のステータス、遷移条件および完了時刻の条件を確認する。 4. MyBatisが予約ステータスを更新し、訂正時は訂正履歴も登録する。 5. 更新後の予約情報を画面に反映する。 **ステータス遷移条件** | 現在のステータス | 許可される遷移 | 条件 | | --- | --- | --- | | `RECEIVED` | `CONFIRMED`、`CANCELED` | 確認済みへの更新、またはキャンセル操作。 | | `CONFIRMED` | `RECEIVED`、`READY`、`CANCELED` | 確認の取消、準備完了への更新、またはキャンセル操作。 | | `READY` | `RECEIVED`、`CONFIRMED`、`COMPLETED`、`CANCELED` | 確認・準備の取消、体験完了への更新、またはキャンセル操作。`COMPLETED`は予約開始日時以後のみ可能。 | | `COMPLETED` | `READY`（訂正のみ） | 通常の更新・キャンセルは不可。スタッフが訂正理由（1〜1000文字）を入力した場合のみ訂正APIで可能。 | | `CANCELED` | なし | 終端状態。通常の更新、キャンセル、訂正は不可。 | 完了後の訂正は、`COMPLETED`から`READY`へ戻す処理のみを実装する。訂正時は予約ID、訂正前後のステータス、訂正日時、操作者のユーザー名、訂正理由を`reservation_status_corrections`に保存する。訂正履歴の一覧表示・取得APIは今回の実装範囲外とする。 **正常時：** 更新後のステータスと予約情報が表示される。訂正時は訂正履歴も同一トランザクションで保存される。 キャンセルはF-008のステータス更新として扱い、予約ステータスを`CANCELED`に変更する。キャンセル後も予約データはMySQLに保持する。物理削除はF-009で別途処理する。 **エラー時：** 不正なステータス値・訂正理由は400、予約が存在しない場合は404、許可されない遷移・終端状態への操作・予約開始前の完了操作は409を返す。訂正APIはスタッフ認証がない場合403を返す。 **遷移先：** スタッフ管理画面 ### F-009 予約削除（Delete） **機能名：予約削除（Delete）** **機能ID：F-009** **画面レイアウト** スタッフ管理画面に「削除」ボタンを配置する。 **入力項目** 予約ID、削除確認操作。 **処理フロー** 1. スタッフが管理画面で削除対象の予約を選択する。 2. 「削除」ボタンを押す。 3. 削除確認ダイアログを表示する。 4. 「削除する」を選択すると削除APIを呼び出す。 5. Spring Securityでスタッフの認証を確認する。 6. Spring BootのController・Service・MyBatis Mapperを経由して、MySQLの対象予約をDELETE文で削除する。 7. 削除成功後、予約一覧を再取得して表示を更新する。 **正常時：** HTTP 204 No Contentを返し、削除した予約は一覧に表示されない。 **エラー時：** 対象予約が存在しない場合はHTTP 404、DB処理に失敗した場合はHTTP 500など適切なエラーを返す。削除失敗時は予約データを保持し、エラーメッセージを表示する。 削除操作はスタッフのみ実行でき、削除前に必ず確認ダイアログを表示する。今回の削除機能は学習用の架空予約データを対象とする。 **遷移先：** スタッフ管理画面 **備考：** データの物理削除は行わず、論理削除によって履歴を残す。 ### F-010 スタッフログイン **機能名：スタッフログイン** **機能ID：F-010** **画面レイアウト** 中央にスタッフID・パスワード入力欄、ログインボタンを配置する。 **入力項目一覧** | 項目名 | データ型 | 必須 | バリデーション | 備考 | | ------ | ------ | -- | ------- | ------ | | スタッフID | String | ○ | 空欄不可 | ログインID | | パスワード | String | ○ | 空欄不可 | 認証情報 | **処理フロー** 1. スタッフが認証情報を入力する。 2. F-012** **処理フロー** 1. 画面とサーバーで入力値を確認する。 2. 不正な入力は登録・更新しない。 3. 項目ごとのエラーを表示する。 4. 内部エラーの詳細は利用者に公開しない。 **正常時：** 処理を継続する。 **エラー時：** 400・401・403・404・500等の状態に応じた応答を返す。 **遷移先：** 操作中の画面 ### REST APIエンドポイント一覧 | "reservationTime": "11:00", "participants": 2, "customerName": "山田 花子", "email": "hanako@example.com", "ageGroup": "20代", "visitType": "FIRST" } ``` **予約登録成功レスポンス** ``` { "id": 1, "reservationNumber": 予約ステータスの定義値は`RECEIVED`、`CONFIRMED`、`READY`、`COMPLETED`、`CANCELED`の5種類である。`/status`に指定できる進捗更新値は`RECEIVED`、`CONFIRMED`、`READY`、`COMPLETED`であり、実際に更新できる値はF-008のステータス遷移条件に従う。`CANCELED`への変更は`/cancel`を使用する。
